# UD2.9 · Servicio de copia de seguridad de PostgreSQL con Flask

**Módulo:** Sistemas Informáticos · 1.º DAM  
**Entorno:** Debian 13  
**Herramientas:** Bash, PostgreSQL, systemd, Flask y subprocess

Trabajaremos como **root dentro del LXC**, por lo que no necesitamos `sudo` para iniciar el servicio.

## 1. Objetivo

Crear un **servicio de Linux** que ejecute un script Bash para hacer una copia de seguridad de PostgreSQL. Cuando accedamos a un endpoint de Flask, Python **iniciará el servicio, esperará a que termine y devolverá el archivo para descargarlo**.

Utilizaremos el **siguiente puerto libre** del rango asignado en la [UD2.7](ud2_7.md), después de los utilizados por SSH, pgAdmin y PostgreSQL. No utilizaremos cron ni timers.

## 2. Crear backup.sh

Creamos la carpeta `/workspace/ud2/copias` y dentro el archivo `backup.sh`:

~~~bash
#!/bin/bash
pg_dump -p 5433 -U postgres -d practica_si -Fc -f /tmp/copia.dump
~~~

**Cambia 5433 por tu puerto PostgreSQL de la UD2.7.** El script genera `/tmp/copia.dump` y termina. Como `pg_dump` es el único comando, si falla, Bash devuelve su código de error al servicio.

## 3. Crear backup.service

Creamos `/etc/systemd/system/backup.service`:

~~~ini
[Unit]
Description=Copia de seguridad de PostgreSQL

[Service]
Type=oneshot
User=postgres
ExecStart=/bin/bash /workspace/ud2/copias/backup.sh
~~~

- **`Type=oneshot`**: ejecuta el script una vez y finaliza.
- **`User=postgres`**: permite ejecutar `pg_dump` con la cuenta Linux de PostgreSQL.
- **`ExecStart`**: indica el script que ejecutará el servicio.

El usuario `postgres` debe poder leer el script y atravesar su carpeta. Si trabajas con otra ruta, actualiza `ExecStart`.

Registramos y probamos el servicio desde una terminal de administración:

~~~bash
systemctl daemon-reload
systemctl start backup.service
journalctl -u backup.service -n 10 --no-pager
~~~

Al terminar correctamente, el servicio quedará normalmente en **`inactive (dead)`**. En un `oneshot` es normal.

## 4. Crear app.py con Flask

En `/workspace/ud2/copias/app.py`:

~~~python
from flask import Flask, send_file
import subprocess

app = Flask(__name__)

@app.route("/backup")
def backup():
    subprocess.run(["systemctl", "start", "backup.service"], check=True)
    return send_file("/tmp/copia.dump", as_attachment=True)

app.run(host="0.0.0.0", port=8081)
~~~

**Cambia 8081 por el siguiente puerto libre que te corresponde según la UD2.7.**

`subprocess.run()` espera a que `systemctl start` termine. Como el servicio es `oneshot`, systemd espera a que termine `backup.sh`. Solo entonces Flask devuelve el archivo mediante `send_file()`.

### Acceder desde el navegador

Como en este LXC iniciamos Flask desde la sesión de `root`, puede ejecutar `systemctl` y leer `/tmp/copia.dump` sin configurar `sudoers`. El script de copia seguirá ejecutándose como el usuario `postgres` gracias a `User=postgres` del servicio.

~~~text
http://IP_DEL_DEBIAN:PUERTO_FLASK/backup
~~~

**Solo para este LXC de prácticas:** ejecutar una aplicación Flask como root aumenta los riesgos. No publiques el endpoint fuera de la red de laboratorio; para un servicio real se utilizaría un usuario sin privilegios y autenticación.

## 5. Diferencia entre ejecutar un proceso y un servicio

Podríamos lanzar el script **directamente desde Python**, sin crear un servicio:

~~~python
subprocess.run(["bash", "backup.sh"])
~~~

O ejecutarlo **como servicio de systemd**, que es lo que hacemos en esta actividad:

~~~python
subprocess.run(["systemctl", "start", "backup.service"])
~~~

| Como proceso Bash | Como servicio systemd |
| --- | --- |
| Lo inicia directamente Python | Lo inicia systemd, a petición de Python |
| Se ejecuta con los permisos de quien lo lanza | Puede ejecutarse con el usuario indicado en `User=` |
| Sus mensajes suelen aparecer en la terminal o en la salida capturada por Python | Sus mensajes y errores se recogen normalmente en `journald` |
| Termina cuando acaba el script | Con `Type=oneshot` también termina cuando acaba el script |
| No tiene una unidad que consultar | Podemos consultar `systemctl status` y `journalctl -u backup.service` |

**La diferencia que nos interesa:** con un servicio de systemd no necesitamos programar archivos `.log`; normalmente los `echo` y errores del script quedan registrados y se pueden consultar mediante:

~~~bash
journalctl -u backup.service -n 20 --no-pager
~~~

El registro lo realiza **systemd-journald**, no el comando `systemctl`.
