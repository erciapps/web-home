    UD2.9 · Servicio de copia de seguridad de PostgreSQL con Flask¶

    Módulo: Sistemas Informáticos · 1.º DAM
    Entorno: Debian 13 (LXC individual)
    Herramientas: PostgreSQL, Bash, systemd, Flask y subprocess

    1. Objetivo¶

    Crear un servicio de Linux que ejecute un script Bash para hacer una copia de seguridad de PostgreSQL. Después, una aplicación Flask permitirá iniciar ese servicio y descargar la copia desde el navegador.

    La actividad se realizará en el Debian individual de las unidades anteriores, usando la base de datos practica_si de la UD2.8. Utilizaremos el siguiente puerto libre de nuestro rango de la UD2.7 para Flask. No utilizaremos cron ni timers.

    Trabajaremos como root dentro del LXC para administrar el servicio. El propio servicio ejecutará el script con el usuario Linux postgres.

    2. Preparar la base de datos¶

    Entra en la base de datos practica_si desde pgAdmin o desde psql. Crea una tabla sencilla para poder comprobar que la copia guarda tanto su estructura como sus datos:

    CREATE TABLE equipos (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(50),
    aula VARCHAR(30)
);

INSERT INTO equipos (nombre, aula) VALUES
('Equipo 1', 'DAM'),
('Equipo 2', 'DAM'),
('Equipo 3', 'DAW');

SELECT * FROM equipos;

    Comprueba que la consulta muestra los tres registros. Si ya tenías otras tablas en practica_si, consérvalas; también se incluirán en la copia.

    3. Crear el script backup.sh¶

    Crea la carpeta /workspace/ud2/copias y dentro el archivo backup.sh:

    #!/bin/bash
set -e

PGPASSWORD="TU_CONTRASENA" pg_dump -h 127.0.0.1 -p 5433 -U postgres -d practica_si -Fc -f /tmp/copia.dump

echo "Copia terminada"

    Adapta TU_CONTRASENA a la contraseña del usuario postgres de PostgreSQL y 5433 al puerto que configuraste en la UD2.8. No confundas el puerto de PostgreSQL con el de Flask.

    El parámetro -h 127.0.0.1 obliga a conectar mediante TCP/IP. Sin él, PostgreSQL puede intentar autenticación peer a través de un socket local, sin utilizar la contraseña.

    -Fc genera un archivo de copia en formato propio de PostgreSQL y set -e detiene el script si falla pg_dump. Así no se mostrará «Copia terminada» cuando haya un error.

    Importante: poner la contraseña en el script simplifica esta práctica de laboratorio, pero no es adecuado para producción. No subas contraseñas reales al repositorio Git.

    4. Crear el servicio backup.service¶

    Crea el archivo /etc/systemd/system/backup.service:

    [Unit]
Description=Copia de seguridad de PostgreSQL

[Service]
Type=oneshot
User=postgres
ExecStart=/bin/bash /workspace/ud2/copias/backup.sh
    • Type=oneshot: ejecuta una tarea y termina.
    • User=postgres: ejecuta el script como el usuario Linux postgres, aunque iniciemos el servicio como root.
    • ExecStart: indica qué comando ejecutará systemd.

    Asegúrate de que el usuario postgres puede acceder a la carpeta y leer backup.sh.

    Registrar y ejecutar el servicio¶

    Cuando creamos o modificamos un archivo .service, hay que indicar a systemd que vuelva a leer las unidades:

    systemctl daemon-reload

    Inicia el servicio y consulta su estado y sus registros:

    systemctl start backup.service
systemctl status backup.service
journalctl -u backup.service -n 10 --no-pager

    Si ha funcionado, aparecerá «Copia terminada» y la ejecución habrá finalizado correctamente.

    Es normal ver inactive (dead) después de una ejecución correcta: un servicio oneshot realiza su trabajo y se detiene.

    Los registros pueden contener errores de ejecuciones antiguas. Para saber qué ocurrió en la última ejecución, observa las fechas de los mensajes más recientes.

    Comprobar la copia¶

    ls -lh /tmp/copia.dump
pg_restore -l /tmp/copia.dump

    El primer comando muestra el tamaño y propietario del archivo. El segundo enumera su contenido: entre las entradas deberían aparecer la tabla equipos y sus datos (TABLE DATA).

    El archivo es binario porque utilizamos -Fc; no se visualiza con cat. pg_restore -l comprueba que se reconoce su estructura, aunque una restauración de prueba sería necesaria para verificar la recuperación completa.

    Si aparece «Permission denied»¶

    El servicio se ejecuta como postgres. Si antes ejecutaste el script manualmente como root, quizá /tmp/copia.dump pertenezca a root y postgres no pueda sobrescribirlo.

    Comprueba el propietario:

    ls -l /tmp/copia.dump

    Si el archivo anterior pertenece a root, puedes eliminarlo desde la terminal de administración y volver a iniciar el servicio:

    rm -f /tmp/copia.dump
systemctl start backup.service

    A partir de entonces, crea las copias a través del servicio para mantener el mismo propietario del archivo.

    5. Crear app.py con Flask¶

    En /workspace/ud2/copias/app.py:

    from flask import Flask, send_file
import subprocess

app = Flask(__name__)

@app.route("/backup")
def backup():
    subprocess.run(["systemctl", "start", "backup.service"], check=True)
    return send_file("/tmp/copia.dump", as_attachment=True)

app.run(host="0.0.0.0", port=8081)

    Cambia 8081 por el siguiente puerto libre de tu rango en la UD2.7. Instala Flask en tu entorno virtual si todavía no lo tienes.

    Cuando el navegador solicita /backup, subprocess.run() inicia el servicio y espera a que termine. Con check=True, un fallo al iniciar el servicio provoca un error en lugar de descargar una copia anterior como si fuese nueva. Cuando termina correctamente, send_file() devuelve el archivo para descargarlo.

    Acceso desde el navegador¶

    Ejecuta Flask desde la sesión de administración del LXC y accede a:

    http://IP_DEL_DEBIAN:PUERTO_FLASK/backup

    Si utilizas la IP del router del instituto, recuerda la redirección de puertos explicada en la UD2.7.

    Solo para prácticas: Flask se ejecuta como root para poder iniciar el servicio sin configurar permisos adicionales. Este endpoint no debe exponerse a Internet; en una aplicación real utilizaríamos autenticación y un usuario con permisos limitados.

    6. Comprobaciones finales¶

    Verifica que el servicio genera la copia, que el archivo pertenece a postgres, que pg_restore -l incluye equipos y TABLE DATA, y que el navegador permite descargarlo mediante /backup.

    Después, inserta otro registro en equipos, vuelve a solicitar /backup y comprueba que el archivo se ha generado de nuevo. Explica por qué el servicio aparece como inactive (dead) después de ejecutarse y cómo distinguirías en journalctl un error antiguo de uno actual.

    7. Diferencia entre proceso Bash y servicio systemd¶

    Podríamos iniciar el script directamente desde Python:

    subprocess.run(["bash", "backup.sh"])

    En esta actividad lo lanzamos a través de systemd:

    subprocess.run(["systemctl", "start", "backup.service"])

    La principal diferencia es que systemd controla la ejecución, permite elegir el usuario con User=postgres y recoge los mensajes del script mediante systemd-journald. No necesitamos crear manualmente un archivo .log para consultar los mensajes con journalctl.

    8. Resumen de systemctl y journalctl¶

    Comando Función
    systemctl start backup.service Ejecutar la copia de seguridad.
    systemctl status backup.service Consultar el estado del servicio.
    systemctl stop nombre.service Detener un servicio en ejecución.
    systemctl restart nombre.service Reiniciar un servicio.
    systemctl enable nombre.service Habilitar su arranque automático si la unidad está preparada para ello.
    systemctl disable nombre.service Deshabilitar el arranque automático.
    systemctl daemon-reload Volver a leer los archivos .service modificados.
    journalctl -u backup.service Consultar todos los registros disponibles del servicio.
    journalctl -u backup.service -n 10 --no-pager Mostrar los diez últimos mensajes.
    journalctl -u backup.service --since today --no-pager Mostrar los registros de hoy.
    journalctl -u backup.service -f Seguir los mensajes nuevos en tiempo real.

    Recuerda: systemctl daemon-reload es necesario al crear o modificar backup.service, pero no cuando solo editas backup.sh. Nuestro servicio oneshot se ejecuta bajo demanda, por lo que no hace falta habilitarlo para el arranque automático.
